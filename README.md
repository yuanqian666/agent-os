# Agent OS：把操作系统本身交给 Agent

> 递归沙箱式 Agent 操作系统 —— 设计与一个 3450 行的 MVP
>
> 一句话：**现在的 Agent 跑在人类的接口里（shell、文件树、GUI）；这个项目把操作系统本身交给 Agent，让 Agent 自己创建进程、调度资源、管理生命周期。**

---

## TL;DR

- 构想：Agent 是操作系统的**执行单元**，不是操作系统的**用户**。隔离靠递归沙箱，通信靠文件读写，路由靠能力表，无中央调度。
- 理论：三大拓扑公理（基因 / 公链 / 族系）+ 控制流第一定律；并**推翻了有性生殖**（树性质下不成立，详见下文）。
- 实现：MVP 已跑通 —— Python 3.11，零 LLM 依赖，四层架构，3450 行，19 个测试全绿，端到端演示通过。
- 状态：构想仍在演化，实现暂停于 MVP（2026-08-23）。

---

## 1. 背景：Agent 跑在人类的接口里

现在的 AI Agent 跑在哪里？在**人类的接口**里。

shell、文件树、GUI、浏览器 —— Agent 的每一次行动，几乎都要借用为人类设计的接口。它需要人类告诉它文件在哪里、权限是什么、命令怎么敲。这有点像让一个员工用对讲机和打字机操作一台服务器：能干，但笨拙。

于是有了这个构想：**把操作系统本身交给 Agent**。Agent 不再是操作系统的用户，而是操作系统的执行单元——自己创建进程（Agent）、自己调度资源、自己管理生命周期。

设计目标：让 AI Agent 在不依赖传统人类接口（shell、文件树、GUI）的情况下，自主运行、协作和调度资源。

---

## 2. 核心思想：四个设计支柱

整个设计由四个互相咬合的原则撑起来：

1. **递归沙箱** — 每个 Agent 住在独立沙箱里，沙箱可以嵌套递归，深度不限。
2. **文件即通信** — Agent 之间不传消息，只读写文件。通信即读写，无中间件。
3. **接口同构** — 所有 Agent、甚至"假装成 Agent"的组件，对外接口完全一致，无法区分。
4. **能力表路由** — 每个父 Agent 维护一张子树能力表，据此决定任务派给谁，无需全局协调。

第 1、2 条是隔离与通信的实现；第 3 条是让"假 Agent"（界面层、HAA）能混进树的合法性依据；第 4 条是让整棵树不需要中央大脑的分布式路由。

---

## 3. 系统设计：四层架构

```
用户
  ↕ 自然语言
界面层（假 Agent 顶层）        ← 翻译用户输入为结构化任务
  ↕ 标准 Agent 接口（任务文件/状态文件）
Agent 树（纯 Agent 递归结构）  ← 任务分解、能力路由、无性繁殖
  ↕ 标准 Agent 接口（任务文件/状态文件）
HAA 层（假 Agent 底层）        ← 封装硬件操作（磁盘/计算/日志…）
  ↕ 系统调用
操作层（微内核/hypervisor）    ← 沙箱创建、capability、资源管理
```

关键设计：**界面层和 HAA 层都是"假 Agent"**——它们的合法性完全来自接口同构（支柱 3）。这带来一个微妙的效果：**Agent 树本身不知道自己的边界在哪**。这既是安全特性（认知隔离），也是运维噩梦（后面 §8 反思会讲）。

---

## 4. 沙箱即契约：一切皆文件

每个 Agent 沙箱是一个标准化的目录：

```
agent_sandbox/
├── task/                 # 任务文件，父可写，子只读
├── status/               # 状态文件，子可写，父只读
│   ├── state             # idle / running / completed / error
│   ├── current_task      # 当前任务描述
│   ├── output            # 任务结果
│   ├── help_requests     # 向上求助请求列表
│   ├── skills            # 能力表（复合 Skill 声明）
│   └── resource_usage    # 资源统计（仅底层可写，不可伪造）
├── skills/               # 技能定义（绝不向上传播）
├── manifest.json         # 元数据、TTL、配额
├── children/             # 子 Agent 沙箱（递归嵌套）
└── state.db              # 内部持久状态（可选）
```

**父子关系完全由文件权限定义**——这是整个设计最核心的决定：

| 通道 | 文件 | 方向 | 效果 |
|---|---|---|---|
| 任务派发 | `task/` | 父写 → 子读 | 子无法伪造任务来源 |
| 状态上报 | `status/` | 子写 → 父读 | 父无法篡改子状态 |

子 Agent 不知道任务来自谁，也不知道状态被谁读。**匿名性是双向的。**

---

## 5. 通信协议：四条单向链路

所有通信通过文件读写完成，无直接消息传递：

1. **任务派发（向下）**：父追加写子 `task` → 子监听取出执行
2. **状态监听（向上）**：子更新 `status` → 父监听变化决策
3. **求助传播（向上递归）**：子写 `help_requests` → 父查子树能力表：有则派发，无则继续上抛
4. **结果返回（向上递归）**：子写 `status/output` + `completed` → 父读取聚合，逐级上抛

这套协议的本质是**单向的、可审计的**：任何一次通信都留下文件，任何一条链路都能用 `cat` 和 `tail -f` 跟踪。这是文件通信方案相比消息总线最大的优点。

## 6. 理论进展：三大公理与控制流第一定律

MVP 之后，构想进入理论演化阶段。核心成果是三公理 + 一定律的严格定义（对齐《严格定义与扩充表述.txt》）：

**公理 1｜基因 = 向下可达性**
拥有某基因 = 能仅通过下放 `task` 文件**最终触达**对应的 HAA。基因不是静态标签，而是系统沙箱结构中自上而下的**物理可达性**。

**公理 2｜公链 = 自下而上的物理权限专线**
从某个 HAA（唯一单例叶子）出发，向上沿父子关系连到 Root 的**唯一链条**，称为该基因的公链。基因与公链一一对应。公链是操作系统的"物理权限专线"与"资源中枢神经"。

**公理 3｜族系 = 任务拆解的嵌套逻辑树**
任意 Agent 的子代及后代构成其族系，族系内可再繁殖形成嵌套子族系。**族系与基因解耦**——族系是任务拆解的"业务部门"，不同族系可携带若干相同基因。

**控制流第一定律：上报顺族系、下放顺公链**
叶子完成计算 / 遇不可达子任务 → status 沿**族系**层层上报至拥有所需基因的祖先节点；祖先通过**公链**将执行指令下发至 HAA。公链与族系的交汇点（祖先节点）天然充当底层 HAA 的**排队机/并发锁**，消除底层资源竞争死锁。

**认知盲区**：每个 Agent 只知"任务从上面来、向下委派"，不知父是否为 Root、子是否为 HAA。

## 7. 为什么有性生殖不成立（树性质推演）

原设计曾考虑"有性繁殖"（跨谱系合并基因），经树性质推演后**判定不成立**：

1. 公理 2 要求每个 HAA 到 Root 存在**唯一**父链（树结构，每个节点唯一父）。
2. 有性生殖 = 两个不同谱系（各自携带不同基因）合并出一个后代 → 该后代需同时继承两条公链的可达性。
3. 在"每个节点唯一父"的树中，一个后代只能拥有一条到 Root 的父链；若允许它同时挂接两个父（双亲），结构立即退化为 **DAG/图**，公理 2 的"唯一公链"与公理 1 的"基因=向下可达性"失去一一对应。
4. 若退而求其次，让合并后的基因在后代内部再挂接 HAA 单例——则基因与公链的对应被打破（一个基因对应多条路径），路由判定（ACL 可达性）失去确定性。
5. **结论**：在"树 + 唯一父链"的公理体系内，唯一合法的繁殖是无性繁殖（基因**子集**复制 + 新谱系标签）；跨谱系合并要么破坏树性质，要么破坏基因↔公链一一对应，二者必居其一。

需要"基因重组"能力的场景（如跨域求助）不繁殖，走**祖先编排**——由同时持有多基因的祖先作为 MapReduce 编排者，按任务步骤向各族系分支/公链派发（`GeneNotOwned` 机制 + `[祖先编排]` 日志）。

## 8. 反思：我睡不着觉的部分

> 以下是设计里我自己没想清楚、最可能塌的地方。写出来是为了让评审者知道该往哪里打。完整版见规格书 §8。

1. **能力表可信度（最致命）**：父 Agent 只能相信子 Agent 的自我声明。认知隔离下，一个 Agent 谎报能力（或 LLM 幻觉出能力）时，父没有任何交叉验证手段。[待验证]
2. **任务生灭 vs 能力累积的矛盾**：每次任务销毁整棵 Agent 树，复合 Skill 积累归零。"无状态残留"的安全承诺与"能力可复用"直接冲突，目前没有好答案。
3. **求助传播的延迟与循环**：最坏 O(树深度) 的文件读写延迟，且可能形成 ping-pong 循环，需要一个防循环机制（补丁，不是设计）。
4. **文件监听的规模上限**：inotify watch 数量有内核上限；树变大后监听/轮询带来 IO 压力。[待核实]
5. **沙箱逃逸 = 一切归零**：一旦某个 Agent 逃出沙箱，整个信任模型塌掉。所以操作层选型（Firecracker/seL4）不是性能问题，是安全底线问题。
6. **认知隔离的反面是诊断困难**：层级不可知 + 匿名父子 = 事故复盘时的黑箱。需要系统级审计日志（由操作层记录），但设计里还没有。

## 9. 实现：四层架构 → 代码映射

MVP 用 **Python 3.11 + watchdog（文件监听）+ multiprocessing（沙箱即进程）**，零 LLM 依赖——用确定性代码验证设计假设。

| 层 | 角色 | 代码模块 |
|---|---|---|
| L1 | 界面层（伪 Agent） | `src/agent_os/interface/cli.py`（演示句规则解析 + JSON 任务） |
| L2 | Agent 树（递归中间层） | `src/agent_os/agent/`（runtime / task_loop / router / reproduction / skill_table） |
| L3 | HAA 层（伪 Agent 底层） | `src/agent_os/haa/`（math_haa / disk_haa / file_read_haa / log_haa） |
| L4 | OS / 微内核层 | `src/agent_os/os_layer/`（supervisor / provisioner / client） |

代码量：约 3450 行 Python，26 个提交，`pyproject.toml` 可安装。

关键实现决策：

- **Root 持有全部基因，但不声明本地技能**（纯协调者）。"缺少执行技能"时触发无性繁殖：把自己的基因**子集**复制给新子沙箱（OS 校验子请求基因 ⊆ 父基因集，越权繁殖被拒——防提权）。
- **HAA 持久托管**：由 OS 层创建、跨任务存活；Agent 通过 genome 中的基因获得向对应 HAA 写任务的 ACL 权限（**基因即访问令牌**）。HAA 不挂 Root children/ 下（否则 Root 天生具备能力，破坏"缺技能→繁殖"的演示语义）。
- **文件化 OS 控制通道**：`sandbox_root/os/requests|replies`（L3↔L4 syscall 边界，符合"一切皆文件"）。
- **两相握手**：任务下发等待 `output.task_id` 与 `state==completed` 双条件，防陈旧状态竞态。

## 10. 端到端演示：一个任务的完整生命周期

演示任务：**"Calculate (5+7)\*3 and save result to disk"**

```
用户 ──▶ 界面层（解析为 JSON 任务）
          └─▶ Root（查能力表：缺 calc_and_save → 无性繁殖）
                ├─▶ Child A（谱系 L1，基因 cpu_calc）──▶ Math_HAA ──▶ 算出 36
                └─▶ Child B（谱系 L2，基因 disk_write）──▶ Disk_HAA ──▶ 落盘 out/t1.txt
                结果 36 沿族系上抛 → Root 路由给 Child B → 完成
                OS 收到 Root completed → 销毁整棵 Agent 树 → 重建 Root
```

演示成功标准（全部自动化断言于 `test_demo_e2e.py`）：

1. 界面层提交复杂任务，显式声明复合技能需求 `calc_and_save`
2. Root 查能力表未命中 → 按基因分解 → 无性繁殖 Child A 与 Child B
3. 子 Agent 上传技能说明 → Root 聚合 → 声明复合技能（能力向上传播）
4. Child A 算出 36 → 结果上抛 → Root 路由给 Child B → Disk_HAA 写盘
5. 控制台日志显示文件读写事件驱动状态流转 + 路由器决策链
6. 任务完成后 OS 层物理清除整棵 Agent 树（仅存 os/ + 持久 HAA + 重建的 Root）

Web 可视化面板（`http://127.0.0.1:8710/`）实时显示：自上而下 Agent 树、繁殖后 HAA 动态挂载到携带其基因的族系子下（符合公链语义）、已销毁节点灰显保留 15s。

## 12. 已知限制与升级路径

- **沙箱隔离**为"进程 + 目录 + OS 进程注册表 ACL"（Windows 上 FS 权限不可靠，ACL 为 OS 判定型）。升级路径：真实 FS 权限 → Docker → Firecracker → seL4。
- **免疫机制**（拓扑蓝图保存、基因足迹审计、谱系隔离）未实现 → V1.1
- **help_requests** 专项路由/UI 未实现 → V1.1
- **资源统计**（resource_usage）为占位，未做强制配额 → V1.1
- **有性繁殖**：已从路线图**移除**（见 §7，理论不成立）

## 快速开始

```bash
pip install -e .            # 可编辑安装

# 一键演示（自动执行 "Calculate 5+7 and save result to disk"）
python scripts/run_demo.py

# 交互式 CLI（演示句 或 JSON 任务；默认内嵌 Web 可视化面板）
python -m agent_os.interface.cli
# 浏览器打开 http://127.0.0.1:8710/ 查看 Agent 树拓扑
# 参数：--no-web 关闭面板；--verbose 显示全部日志（含 EVENT 文件事件）

# 测试（19 用例）
python -m pytest tests/ -v
```

环境变量（可选）：`AGENT_OS_OUT_ROOT`（Disk_HAA 落盘目录）、`AGENT_OS_LOG_FILE`（跨进程日志文件）。
