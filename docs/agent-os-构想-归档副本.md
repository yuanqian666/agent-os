# 关于 Agent OS 的一些构想

> 一份尚未经验证的设计笔记。没有 MVP，没有 benchmark，很多环节我自己都没想清楚。写出来，是想请有能力评定架构的人帮我看看：哪里会塌。

---

## 0. 为什么会有这个构想

现在的 AI Agent 跑在哪里？在**人类的接口**里。

shell、文件树、GUI、浏览器——Agent 的每一次行动，几乎都要借用为人类设计的接口。它需要人类告诉它文件在哪里、权限是什么、命令怎么敲。这有点像让一个员工用对讲机和打字机操作一台服务器：能干，但笨拙。

于是有了这个构想：**把操作系统本身交给 Agent**。Agent 不再是操作系统的用户，而是操作系统的执行单元——自己创建进程（Agent）、自己调度资源、自己管理生命周期。

设计目标：让 AI Agent 在不依赖传统人类接口（shell、文件树、GUI）的情况下，自主运行、协作和调度资源。

这篇笔记的结构：先说四个设计支柱，再展开四层架构、沙箱契约、通信协议、能力体系、递归透明性和生命周期，最后是可行性评估和 MVP 路线。**可行性部分我特意放在最后**——因为先看完设计，你才知道我哪些地方在裸奔。

---

## 1. 四个设计支柱

整个设计由四个互相咬合的原则撑起来：

1. **递归沙箱** — 每个 Agent 住在独立沙箱里，沙箱可以嵌套递归，深度不限。
2. **文件即通信** — Agent 之间不传消息，只读写文件。通信即读写，无中间件。
3. **接口同构** — 所有 Agent、甚至"假装成 Agent"的组件，对外接口完全一致，无法区分。
4. **能力表路由** — 每个父 Agent 维护一张子树能力表，据此决定任务派给谁，无需全局协调。

第 1、2 条是隔离与通信的实现，第 3 条是让"假 Agent"能混进树的合法性依据，第 4 条是让整棵树不需要中央大脑的分布式路由。

---

## 2. 四层架构

```
用户
  ↕ 自然语言
界面层（假 Agent 顶层）
  ↕ 标准 Agent 接口（任务文件/状态文件）
Agent 树（纯 Agent 递归结构）
  ↕ 标准 Agent 接口（任务文件/状态文件）
HAA 层（假 Agent 底层）
  ↕ 系统调用
操作层（微内核/硬件）
```

从上到下逐个说：

**界面层（假 Agent 顶层）**——不是 Agent，不参与任务分解或资源管理。它只做两件事：把用户输入翻译成结构化任务，写进根主 Agent 的 `task` 文件；读根主 Agent 的 `status` 文件，把结果翻译回自然语言给用户。它实现与真实父 Agent 完全相同的接口，所以**根主 Agent 无法区分界面层和真实父 Agent**。

**Agent 树（纯 Agent 递归结构）**——每个 Agent 运行在独立沙箱中，遵循相同的父子协议。树递归定义：根主 Agent 可创建子 Agent，子可创建孙，深度不限。每个 Agent 都自认为是中间层：有上级（任务来源）、有下级（可派发任务），无法判断自己在树中的实际位置。这条"匿名性"原则是整个设计里我最喜欢、也最可疑的部分，后面第 6 节细说。

**HAA 层（Hardware Abstraction Agent，假 Agent 底层）**——不是 Agent，不参与递归或决策。每个 HAA 封装一类硬件操作（内存分配、磁盘读写、网络收发等），以标准 Skill 形式暴露，对外表现与真实子 Agent 完全一致。**叶子 Agent 无法区分 HAA 和真实子 Agent**。

**操作层（微内核/硬件）**——确定性、可形式化验证的微内核或 hypervisor（候选：seL4）。提供物理资源管理：内存页、CPU 时间、设备访问；只提供沙箱创建原语和 capability 管理，**不维护 Agent 树结构**；为 HAA 提供系统调用接口。

注意界面层和 HAA 层都是"假 Agent"——它们的合法性完全来自接口同构。这带来一个微妙的效果：**Agent 树本身不知道自己的边界在哪**，这既是安全特性（认知隔离），也是我后面要说的风险来源。

## 3. 沙箱即契约

每个 Agent 沙箱是一个目录，结构标准化：

```
agent_sandbox/
├── task/                 # 任务文件，父可写，子只读
├── status/               # 状态文件，子可写，父只读
│   ├── status            # 当前状态：idle / running / completed / error
│   ├── current_task      # 当前任务描述
│   ├── output            # 任务结果
│   ├── help_requests     # 向上求助请求列表
│   ├── skills            # 能力表（复合 Skill 声明）
│   └── resource_usage    # 资源使用统计（由底层强制更新）
├── skills/               # 技能定义文件（可选）
├── manifest.json         # Agent 元数据、资源配额、权限需求
├── children/             # 子 Agent 沙箱目录（递归嵌套）
│   ├── child_a/
│   └── child_b/
└── state.db              # 内部持久状态（可选）
```

这个结构最核心的设计决定是：**父子关系完全由文件权限定义**。

- 拥有子沙箱 `task` 文件**写**权限者，即为父。
- 拥有子沙箱 `status` 文件**读**权限者，即为父。

两条单向通道：

| 通道 | 文件 | 方向 | 效果 |
|---|---|---|---|
| 任务派发 | `task/` | 父写 → 子读 | 子无法写入或修改，无法伪造任务来源 |
| 状态上报 | `status/` | 子写 → 父读 | 父无法篡改子状态，只能监听 |

子 Agent 不知道任务来自谁，也不知道状态被谁读。匿名性是双向的。

关键状态字段（如 `resource_usage`）由底层操作层强制更新，Agent 自己写不了——这是唯一一处打破"全文件"原则的特权通道，目的是让资源统计不可伪造。

## 4. 通信协议

所有通信通过文件读写完成，无直接消息传递。四条链路：

**① 任务派发（向下）**
1. 父 Agent 将任务描述追加写入子 Agent 的 `task` 文件。
2. 子 Agent 的运行时监控 `task` 文件，检测到新任务后取出执行。
3. 执行过程中持续更新自己的 `status` 文件。

**② 状态监听（向上）**
1. 子 Agent 更新 `status` 文件中的相应字段。
2. 父 Agent 监听子 `status` 文件变化（事件通知或轮询）。
3. 父 Agent 读取变化，做出决策：继续派发、调整资源、向上求助。

**③ 求助传播（向上递归）**
1. Agent 无法解决当前任务时，将求助请求写入自己的 `status/help_requests`。
2. 父 Agent 读到后检查自己的子树能力表：
   - 有匹配能力 → 作为任务派发给对应子 Agent；
   - 无匹配能力 → 把请求追加到自己的 `help_requests`，继续向上传播。
3. 递归直到某个祖先节点的子树具备解决能力；若到达根主 Agent 仍无解，由界面层返回错误给用户。

**④ 结果返回（向上递归）**
1. 子 Agent 完成任务，将结果写入 `status/output`，状态置为 `completed`。
2. 父 Agent 监听到完成，读取结果，必要时汇总多个子结果。
3. 递归向上，最终根主 Agent 把最终结果写进自己的 `status`，界面层读取后返回用户。

这套协议的本质是**单向的、可审计的**：任何一次通信都留下文件，任何一条链路都能用 `cat` 和 `tail -f` 跟踪。这是文件通信方案相比消息总线最大的优点，也是我选择它的核心理由。

## 5. 能力体系

**能力表（Skill Table）**：每个 Agent 维护一张，内容为：

```
能力表(agent) = 自身声明技能 ∪ (∪ 每个子 Agent 的能力表)
```

- 叶子 Agent（通常是 HAA）的能力表只含自身声明的原子技能；
- 根主 Agent 的能力表等于整个系统当前可用的全部技能；
- 聚合由父 Agent 监听子状态自动完成，子能力表变化逐级向上传播。

**复合 Skill**：允许中间 Agent 将多个子 Agent 的技能编排成高级技能，对外只暴露简洁接口。意图是让能力可复用、可累积，避免重复创建相同功能的子树。

**权限**：能力表对自身可写可改，对父只读——父不能篡改子声明的能力。

**用户可见能力**：根主 Agent 通过界面层把能力表提交给用户，用户可以直接选择某个能力并指定输入，界面层将其转换为任务写入根主 Agent。

设计意图很清楚：**能力是声明式的、自下而上聚合的**，路由是自上而下分发的。父 Agent 永远基于"孩子说自己会什么"来做决策——这句话我加了粗，因为它是整个体系最脆弱的假设，第 8 节再说。

## 6. 递归透明性（我最喜欢的部分）

由于所有层级的接口完全一致：

- 每个 Agent 都认为自己是中间层——上面有父，下面有子；
- 根主 Agent 认为自己上面有父（界面层伪装的）、下面有子（HAA 伪装的）；
- 叶子 Agent 认为自己上面有父、下面也有子（HAA 伪装的）。

**因此没有任何 Agent 能通过接口差异判断自己的实际层级。**

这带来两个效果：

**认知隔离（安全向）**：子 Agent 无法向上通信，只能被动被父监听；父 Agent 身份匿名，子 Agent 无法针对性地攻击"那个派任务给我的人"。层级不可知 = 攻击面不可见。

**层级不可知（诊断向）**：如果某个 Agent 的行为异常，你没法通过它自己的视角知道它在哪里、它是谁的孩子——这个"设计优点"会在运维时反噬，后面细说。

另外一个推论：求助沿状态文件向上传播、任务沿任务文件向下路由，每个父 Agent 只需看自己的能力表就能决策——**路由是局部决策，不需要任何全局协调者**。这是整棵树可以无限长下去而不需要一个"中央调度"的原因。

## 7. 生命周期

**初始化**：启动操作层 → 创建所有 HAA（持久，跨任务存在）→ 创建界面层（持久）→ 创建根主 Agent，连接 task 文件与界面层，把 HAA 沙箱挂载进它的 `children/` → 根主 Agent 开始监控 task 文件。

**任务执行**：用户提交任务 → 界面层写入根主 Agent 的 task 文件 → 根主 Agent 查能力表，有匹配技能则路由，没有则创建子 Agent 构建能力 → 递归分解执行直至 HAA 完成底层操作 → 结果沿 status 逐级向上返回。

**销毁与重置**（任务生灭）：
1. 根主 Agent 把最终结果写入 status，界面层读取并反馈用户；
2. 操作系统**销毁整棵 Agent 树**（根主 Agent 及其所有子孙沙箱）；
3. HAA 和界面层保持不变；
4. 系统自动创建新的根主 Agent，重新连接，等待下一个任务。

每次任务后销毁整棵树，意味着**无状态残留**：即使恶意代码控制了某个 Agent，影响仅限于当前任务周期。这是非常激进的安全姿态——也是成本很高、和"能力累积"目标直接冲突的姿态，第 8 节会展开。

## 8. 可行性评估

> 这一节是我写给自己看的拆台笔记，也是请你看的重点。结论先行：**我认为有条件可行**——但有几个点如果不解决，整个设计就是纸上的。

### 8.1 我比较有信心的部分

**文件即通信，已经被业界反复实践。** 这不是空中楼阁：DropSite（JSON 文件 inbox/active/done 目录）、OACP（YAML 消息 + 收件箱）、FCoP（TASK-*.md / REPORT-*.md / ISSUE-*.md）、abq（零 broker 文件总线）等真实项目都在用文件系统做 Agent 间协调。共同点是零依赖、跨运行时、`cat` 即可调试。这一支柱我认为是实的。

**沙箱隔离路径清晰。** Docker 容器 → Firecracker 微 VM → seL4 微内核，是一条被验证过的升级路径：已有团队（Declaw）明确为 Agent 沙箱从 Docker 迁移到 Firecracker，理由是容器共享内核、隔离边界不适合承载不可信 Agent；而 seL4 具备机器可验证的形式化证明和 capability 机制（authority confinement），与"文件权限即关系"的设计哲学天然同构。工程量大，但方向不虚。

### 8.2 让我睡不着觉的部分

**① 能力表可信度（最致命）。** `status` 是子写父读，父 Agent 只能相信子 Agent 的自我声明。认知隔离下，一个 Agent 谎报能力（或 LLM 幻觉出能力）时，父没有任何交叉验证手段。真实系统里 LLM Agent 高估自己能力是常态——这条路从"能力表"到"正确路由"之间隔着一整个可靠性问题。[待验证]

**② 任务生灭 vs 能力累积的矛盾。** 每次任务销毁整棵 Agent 树，复合 Skill 积累归零。如果系统每次都要从零长树，那么"能力可复用、可累积"（第 5 节）从何谈起？要么销毁时导出能力表存档、要么部分子树跨任务存活——但这又削弱"无状态残留"的安全承诺。这是设计内部的一处自相矛盾，我目前没有好答案。

**③ 求助传播的延迟与循环。** help_requests 逐级上传，最坏情况 O(树深度) 的文件读写延迟；且父把求助派回给子、子又解决不了再上传，可能形成 ping-pong 循环。需要一个防循环机制（如请求携带路径记录），但这是补丁，不是设计。

**④ 文件监听的规模上限。** inotify 有 watch 数量上限（内核参数限制，具体值依环境而定）[待核实]；Agent 树变大后，父对大量子的轮询/监听会带来 IO 压力。文件方案的"简单可调试"在规模面前会退化。

**⑤ 沙箱逃逸 = 一切归零。** 文件权限隔离建立在"沙箱不逃逸"的前提下。一旦某个 Agent 逃出沙箱（Docker 逃逸、内核漏洞），它就能伪造 task 文件、篡改 status——整个信任模型塌掉。所以操作层选型（Firecracker/seL4）不是性能问题，是安全底线问题。

**⑥ 认知隔离的反面是诊断困难。** "任何 Agent 都无法判断自己的层级"作为安全特性很妙，作为运维噩梦也很妙：故障定位时你不知道该问谁、该信任谁的报告。层级不可知 + 匿名父子 = 事故复盘时的黑箱。需要系统级的审计日志（由操作层记录，而非 Agent 自报），但这个设计里还没有。

### 8.3 备选方案对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| **文件通信（本设计）** | 零依赖、可审计、任何状态可用 cat 查看 | 延迟高、规模上限、无实时推送 |
| **消息总线（NATS/RabbitMQ）** | 实时、可观测、解耦 | 引入 broker 依赖；abq 等项目的立场是"文件够用时别上中间件" |
| **编排框架（LangGraph/AutoGen 等）** | 开箱即用的控制流 | 做编排不做 OS 级隔离；Agent 仍是"库里的对象"而非"系统里的公民" |
| **AIOS 等学术"Agent OS"** | 聚焦 LLM 资源调度与并发管理，有论文支撑 | 关注调度层而非递归沙箱 + 文件原语；与本文构想的层面不同 |

本设计相对它们的差异点：**把隔离、通信、路由都原语化到"目录与权限"这个层面**，Agent 树成为一等公民而非框架内部结构。

## 9. MVP 路线（零 LLM 依赖）

原型阶段不引入任何 LLM，用确定性代码验证设计假设：

- **运行时**：Python 编写的确定性 Agent 运行时，任务和状态用 JSON 文件。
- **沙箱**：Docker 容器 + 文件系统权限隔离。
- **监听**：inotify 事件通知。
- **界面层**：先接受结构化命令（JSON），不引入自然语言；需要时再接入本地小模型（如 Ollama 跑 Qwen 2.5 1.5B）或便宜 API。
- **HAA**：独立进程，暴露标准沙箱目录，内部通过系统调用操作资源，对上层表现为普通子 Agent。

**资源与成本**：原型阶段单人可做——Python + Docker + inotify 均为免费开源工具，无 LLM API 依赖（结构化命令即可跑通全链路），时间量级为周而非月。接入 LLM 后成本模型是另一回事：每个 Agent 节点每次决策一次调用，树深 × 任务步数 × token 是线性叠加，暂未估算量级，属于原型之后的课题。若走 Firecracker，需额外运维 KVM 虚拟化环境；seL4 路线则是年为单位的研究级投入。

**验证清单**（每项对应一个设计假设）：

- [ ] 递归创建：Agent 能否用代码创建符合标准格式的子沙箱并正确设置权限？（对应 §3）
- [ ] 状态监听：父能否可靠感知子的状态变化？（对应 §4②）
- [ ] 求助传播：三级树中，求助能否正确逐级上传并在有能力的节点被截获？（对应 §4③）
- [ ] 能力表聚合：子能力变化能否自动逐级传播到根？（对应 §5）
- [ ] 匿名性：伪装成父/子的组件能否被 Agent 识别出来？（对应 §6——我赌识别不出来，输了更好，说明认知隔离是真的）

**底层替换路径**：Docker 容器 → Firecracker microVM → seL4 微内核，逐步提升隔离强度和透明性。

## 10. 结尾：我想被问的问题

这个设计我最想听别人怎么评价的，是这几个问题：

1. **能力表可信度**有没有比"信子的话"更好的机制？还是说这只能靠 Agent 本身的可靠性兜底？
2. **任务生灭与能力累积**的矛盾，你们会选哪边？有中间路线吗？
3. **递归透明性**作为安全机制，真的值得吗？它的运维代价（诊断困难）怎么对冲？
4. 文件通信在什么规模上会先撑不住？
5. 如果你们来做这个 OS，第一层（微内核）会怎么选？

如果你看到了这里，欢迎直接指出设计里你认为会塌的地方——这正是我写这篇笔记的目的。

## 11. 理论进展归档（2026-08-25，MVP 完成后）

> 本节由 pi agent 根据 `Agent_OS工作区/agent_os/README.md` 中已落地的公理体系与用户口述整理归档。**推导细节为归档时重构，请作者校订。**

MVP（2026-08-23 完成，19 测试全绿）之后，构想进入理论演化阶段，关键进展：

### 11.1 三大公理的严格定义

- **公理 1｜基因 = 向下可达性**：拥有某基因 = 能仅通过下放 task 文件**最终触达**对应的 HAA（ACL 判定可达）。基因不是静态标签，而是可达性的简写。
- **公理 2｜公链 = 自下而上的物理权限专线**：每个 HAA 是唯一单例叶子，向上经父子关系连到 Root 的**唯一**链条。基因与公链一一对应（gene → HAA 映射）。
- **公理 3｜族系 = 任务拆解的嵌套逻辑树**：每个 Agent 的子代与后代构成其族系，族系内可再繁殖形成嵌套子族系。**族系与基因解耦**——族系是任务拆解的"业务部门"，不同族系可携带若干相同基因。

### 11.2 控制流第一定律

**上报顺族系、下放顺公链**：叶子完成计算 / 遇不可达子任务 → status 沿族系层层上报至拥有所需基因的祖先；祖先经公链将执行指令下发至 HAA；祖先节点天然充当并发排队机。

### 11.3 有性生殖不成立（树性质推演）

原设计曾考虑"有性繁殖"（跨谱系合并基因）作为 V1.1 能力，经树性质推演后**判定不成立**：

1. 公理 2 要求每个 HAA 到 Root 存在**唯一**父链（树结构，每个节点唯一父）。
2. 有性生殖 = 两个不同谱系（各自携带不同基因）合并出一个后代 → 该后代需同时继承两条公链的可达性。
3. 在"每个节点唯一父"的树中，一个后代只能拥有一条到 Root 的父链；若允许它同时挂接两个父（双亲），结构立即退化为 **DAG/图**，公理 2 的"唯一公链"与公理 1 的"基因=向下可达性"失去一一对应。
4. 若退而求其次，让合并后的基因在后代内部再挂接 HAA 单例——则基因与公链的对应被打破（一个基因对应多条路径），路由判定（ACL 可达性）失去确定性。
5. **结论**：在"树 + 唯一父链"的公理体系内，唯一合法的繁殖是无性繁殖（基因**子集**复制 + 新谱系标签）；跨谱系合并要么破坏树性质，要么破坏基因↔公链一一对应，二者必居其一。

> 推论：需要"基因重组"能力的场景（如跨域求助）不应走繁殖路线，而应走**祖先编排**（见 11.4）——由同时持有多基因的祖先作为 MapReduce 编排者派发。

### 11.4 其余演化结论（MVP 中已验证/已落地）

- **跨域缺基因 → help_request 沿族系上抛，不横向杂交**：由同时拥有多基因的祖先作为编排者（`GeneNotOwned` 机制 + `[祖先编排]` 日志）。
- **HAA 是权限令牌而非技能**（机制与策略分离）：HAA 声明 `token_<gene>`（物理机制说明）；策略/技能属于 LLM Agent 侧。
- **保留能力 = 保留祖先调度蓝图**：runtime_log 记录每次派发步骤（Topology DAG），随任务记录持久化。
- **skill = 基因组合的编排说明**：子 Agent 把技能（含 required_genes/编排说明）写入 status/skills 向上传播，父聚合后编排复合技能。

### 11.5 归档状态

- **当前状态**：构想演化中；实现暂停于 MVP（2026-08-23 完成，可运行、可演示）。
- **唤醒条件**：① 本科 OS 课程/课设开始；② 考研结束后的寒暑假；③ 读研期间（若研究方向相关，可作为课题）。
